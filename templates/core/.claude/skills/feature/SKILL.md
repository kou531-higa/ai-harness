# /feature：機能開発

対象：$ARGUMENTS

## 手順

1. **読む**：`gh issue view` でチケットを読み、対象の仕様（SPEC-xxx）と AC を確かめる。
   仕様の status が `approved` でなければ止める。
2. **計画する（コードは書かない）**：関連コード・共通部品・既存の書き方を読み、次をチケットにコメントする。
   - 変更するファイル、方針、使う共通部品
   - AC ごとのテストの名前
   - 400行を超えそうなら分割案
3. **人の OK を待つ**：計画を示したら、そこで止まって返事を待つ。OK が出るまで実装しない。
4. **テストを先に書く**：ブランチ `feat/<番号>-<説明>` を切り、AC ごとにテストを書く。
   実行して**落ちること**を確かめ、そのログを残してコミットする。
5. **実装する**：テストが通るまで実装する。整形と Lint はフックが自動でかける。
6. **確かめる**：`make check` を実行する。
7. **PR を作る**：`gh pr create`。テンプレートの「人が判断すべき点」と「証拠」（コマンドと出力、落ちたテストのログ）を埋める。
8. **指摘に対応する**：レビューの指摘を直す。

## 終わってよい条件

- AC すべてにテストがあり、`make check` が通っている
- PR の「人が判断すべき点」と「証拠」が埋まっている

## 止まって人へ戻す条件（/decision-memo、ラベル ai-stop:<理由>）

| 状況 | 理由 |
|---|---|
| 仕様にない振る舞いが必要になった、仕様に TBD がある | `spec-undecided` |
| 仕様どうしが食い違っている | `spec-conflict` |
| 共通部品の追加・変更が必要 | `shared-component` |
| 400行を超えそうで、分割もできない | `pr-too-large` |
| 同じテストの失敗を2回直しても通らない | `two-failures` |

## してはいけないこと

- 計画の OK の前に実装する
- テストを実装に合わせて後から書く、テストを消す・skip する
- PR をマージする（人が判断する）
