# /feature：機能開発

対象：$ARGUMENTS

## 手順

1. **読む**：`gh issue view` でチケットを読み、対象の仕様（SPEC-xxx）と AC を確かめる。
   仕様の status が `approved` でなければ止める。
   **もう済んでいるとき**：チケットの中身がすでに main に入っているなら、ブランチと PR は作らない。証拠（ファイルと行・入れた PR・回したテストとその結果）をチケットにコメントして閉じ、そこで終える。「閉じてよいか」と人に聞いて止まらない（人はコメントを見て開き直せる）。
   **関係する決定を集める**：チケット・仕様・PR の本文とコメントに出てくる `#番号` のうち、判断チケット（`needs-decision`）を `gh issue view` で読み、閉じたものは最後の「決定：」のコメントを、開いているものは「判断待ち」として並べる。決まりの一覧（`docs/decisions/rules.md`）で当てはまる R-ID も並べる。この一覧を計画（PR の本文）の最初に「関係する決定」として書き、それに反することはしない。開いている判断待ちに関わる所は、決まるまで進めない。
   **決定を書き戻す**（着手の前に）：チケットのコメントにある決定（「〜にする」「〜で合意」など）は、判断記録（`docs/decisions/DEC-xxx`、型は `_template.md`）か仕様に書き戻してから実装する。**コメントは正本にしない**（あとから読む AI と人が読み落とすため）。書き戻すまで実装を始めない。仕様を変えるときは、変えた行を PR の「人が判断すべき点」に挙げる。
2. **計画する**：関連コード・共通部品・既存の書き方を読み、次をチケットにコメントする。
   - 変更するファイルと、影響する範囲（`/impact` の表。画面・API・バッチ・DB・テスト）
   - 方針と、使う共通部品
   - AC ごとのテストの名前
3. **大きい変更のときだけ、人の OK を待つ**。次のどれかに当たれば、計画を示して止まる。
   - 本体（テストを除く）が400行を超えそう（分割案も示す）
   - 共通部品・カタログ・DB の構造（マイグレーション・プロシージャ）を変える
   - 新しい画面や API を足す

   当たらなければ、計画をコメントしたまま次へ進む（人はいつでも止められる）。

   **分けるとき**：1チケットを分けるときも、積み重ねにせずそれぞれ main から作る。前の PR の枝から切らない。分割の途中ではチケットを閉じない。最後の PR だけ `Closes #番号`、ほかは `Refs #番号` と書く。
4. **今の振る舞いを固定する**：`/impact` で「テストなし」の所は、変える前に今の振る舞いを確かめるテストを書いて通しておく。
   テスト名は `char_<対象>`。今の振る舞いがおかしく見えても、テストはそのとおりに書き、PR の「人が判断すべき点」に挙げる（直すかは人が決める）。
5. **テストを先に書く**：ブランチ `feat/<番号>-<説明>` を切り、AC ごとにテストを書く。
   実行して**落ちること**を確かめ、そのログを残してコミットする。
6. **実装する**：テストが通るまで実装する。整形と Lint はフックが自動でかける。
7. **動かして確かめる**：`/verify` の手順で、検査・起動・画面のテスト・実際の操作まで通し、証拠を残す。
8. **決定記録を1本書く**（必須）：この変更で決めたことを、`docs/decisions/_template.md` の型で `docs/decisions/DEC-<番号>-<短い名前>.md` に書く。中身は、なぜ・合意した範囲・先送りしたものと理由・根拠（仕様の版・元の位置）。番号を PR の「関係する DEC」に書く（CI が、参照した DEC のファイルがあるか確かめる）。
9. **PR を作る**：`gh pr create`。テンプレートの「関係する DEC」「人が判断すべき点」と「証拠」（コマンドと出力、落ちたテストのログ）を埋める。
10. **指摘に対応する**：レビューの指摘を直す。

## 終わってよい条件

- AC すべてにテストがあり、`make check` と画面のテストが通っている
- PR の「人が判断すべき点」と「証拠」が埋まっている
- 決定記録が1本あり、PR の「関係する DEC」に番号がある。チケットのコメントにだけある決定が残っていない

## 止まって人へ戻す条件（/decision-memo の型で判断チケットを起票する。ラベル ai-stop:<理由>）

| 状況 | 理由 |
|---|---|
| 仕様にない振る舞いが必要になった、仕様に未確定の印がある | `spec-undecided` |
| 仕様どうしが食い違っている | `spec-conflict` |
| 顧客の合意が要る扱いが出てきた | `customer-agreement` |
| 共通部品・カタログの追加・変更が必要 | `shared-component` |
| 本体が400行（テストが800行）を超えそうで、分割もできない | `pr-too-large` |
| 同じテストの失敗を2回直しても通らない | `two-failures` |

## してはいけないこと

- 大きい変更なのに、計画の OK の前に実装する
- テストを実装に合わせて後から書く、テストを消す・skip する
- 状態の判定を直接書く（`catalog/` を使う）
- チケットのコメントにだけある決定に従って実装する（先に判断記録か仕様に書き戻す）
- 分けた PR を積み重ねる（前の PR の枝から切る）
- PR をマージする（人が判断する）
