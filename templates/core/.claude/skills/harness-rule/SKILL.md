# /harness-rule：決めたことを決まりにする

対象：$ARGUMENTS

同じ種類の判断が何度も人に来るのは、仕組みの穴。決まった基準を決まりにして、次からは人に来ないようにする。
ただし、決まりは人の判断の代わりになるので、**採用するのは人**（この手順は PR を作るところまで）。

## 手順

1. **決定を読む**：判断チケットの決定のコメント、または `docs/decisions/DEC-xxx.md`。決定者と日付があるかを確かめる。
   決定の記録がなければ、`docs/decisions/_template.md` の形で判断記録を書く（決めた人の言葉をそのまま写し、足さない）。
2. **一般化する**：その決定を「次に同じ種類の論点が出たら、こうする」の形に書き直す。次の3つを必ず書く。
   - 当てはまる場合（例：顧客1社だけが使う状態）
   - すること（例：新しい状態を作らず、意味の近い既存の状態に対応づける）
   - **当てはまらない場合**（例：意味の近い状態が2つ以上あるか、1つもない → 人へ戻す）
3. **確かめる**：今ある仕様の未確定（`docs/decisions/undecided.md`）と過去の判断チケットに当ててみて、この決まりで答えが出るもの・出ないものを並べる。
   元の決定と違う答えになる過去の例があれば、一般化しすぎ。決まりを狭める。
   ほかの決まり（`docs/decisions/rules.md`）と食い違わないかも見る。
4. **置き場所を決める**：決まりは必ず `docs/decisions/rules.md` に1行足す。必ず守らせたいものは、加えて次から選ぶ（強い順）。
   - 検査（スクリプト・禁止パターン・カタログ）：AI が守れなかったときに機械で止まる
   - 層の `CLAUDE.md`：その層を触るときだけ読まれる
   - 直下の `CLAUDE.md`：毎回読まれる（150行の上限があるので、最後の手段）
   ハーネスの設定（`.claude/`・CI）を変える案は、PR の本文に書くだけにする（設定は人が変える）。
5. **PR を作る**：変更は、判断記録・`rules.md` の1行・置き場所の変更だけ。本文に、3 で並べた「この決まりで答えが出る・出ない」と、元の判断チケットへのリンクを書く。

## 終わってよい条件

- 判断記録（決定者と日付つき）と、`rules.md` の1行（当てはまらない場合つき）がある
- この決まりで答えが出る例・出ない例が、PR の本文に1つ以上ずつある
- PR に `needs-decision` が付いている（採用するかは人が決める）

## 止まって人へ戻す条件

| 状況 | 理由 |
|---|---|
| 決定者・日付が分からない（決まったのかが分からない） | `spec-undecided` |
| ほかの決まりや仕様と食い違う | `spec-conflict` |
| 元の決定より広く一般化しないと決まりにならない | `customer-agreement` |
| ハーネスの設定や CI を変えないと守らせられない | `shared-component` |

## してはいけないこと

- 決定にない内容を、決まりに足す（「ついでに」決めない）
- 決まりを PR を通さずに `rules.md` に書く
