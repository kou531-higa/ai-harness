# /review：AI レビュー

対象：$ARGUMENTS

## 手順

1. **PR を手元に**：`gh pr checkout <番号>`。基準は `gh pr view <番号> --json baseRefName` の `origin/<ブランチ>`。
   この会話でその PR を書いていたなら、`/clear` してから始める（書いた考えに引きずられるため）。
2. **何回目かを見る**：`.harness/reviews/pr-<番号>.json` があれば2回目から。前回の指摘の台帳（番号・重さ・状態）と、前回見たコミット（`head`）を読む。
   2回目からは、**前回からの差分と未解決の指摘だけ**を見る。見る範囲は `git diff <前回の head>...HEAD` と、未解決の指摘の場所。
3. **割り振る**：`python3 scripts/review_route.py --base origin/<ブランチ> --json`。2回目からは、前回からの差分に出てくるファイルだけを渡す。
   `--generic` のときは、担当を `general` の1体だけにして、すべてのファイルを渡す（担当別と比べるため）。
4. **並行で読ませ、全員を待つ**：割り振られた担当ごとに、サブエージェント `reviewer` を1体ずつ、同じ返答の中で同時に起動する。
   - レビュー役は**前景**で動かす（背景にしない）。**全員の結果がそろってから**次へ進む。1体でも返っていなければ、まとめない・終えない
   - 渡すのは次だけ。観点の一覧 `.claude/review/<担当>.md`／その担当のファイルの一覧と基準／関係する仕様の ID（PR の本文やチケットにあれば）／2回目からは、その担当の未解決の指摘（番号・場所・内容）
   - PR の説明・書いた人の考え・ほかの担当の結果は渡さない
   変更に `catalog/` が含まれるときは、`/catalog-challenge` の手順 2〜4 も行い、反証役（`catalog-challenger`）の結果を「反証」の節に載せる。
5. **合わせる**：同じ場所の指摘は1件にまとめ、重い方の重さと、見つけた担当をすべて書く。根拠のない指摘は落とす。
   下の「収束の決まり」で、番号を振り、状態を付け、上限で絞る。
6. **未カバーを並べる**：次の3つを1つの節にする。
   - どの担当にも割り振られなかったファイル（`uncovered`）
   - レビュー役が「未カバー」「見ていない」と返した所
   - 重要な所の変更（`critical_changed`）：AI が見ても、人も見る
7. **コメントする**：下の型で `gh pr comment <番号> --body-file <ファイル>`。**コメントするまで終えない。**
8. **記録する**：`.harness/reviews/pr-<番号>.json` に、回数・見たコミット（`head`）・指摘の台帳（番号・重さ・状態・場所）・担当・重さごとの件数・未カバーの件数・`--generic` かどうか・重大な新規の件数を書く（次の回と、あとの集計が読む）。

## 収束の決まり

「見つけて」と頼むと、何かを見つけてしまう。回を重ねても論点が増え続けないように、次を守る。

- **指摘に番号を振る**：`R1-3`（1回目の3件目）の形。次の回では、前の番号ごとに **解決・見送り・新規** のどれかを付けて追う。見送りには理由を書く
- **重さの下限**：必須にしてよいのは、正しさ（壊れる・値がずれる）・仕様の矛盾・セキュリティ（個人情報を含む）だけ。それ以外は推奨か細かいにする
- **1回の指摘の上限**：必須と推奨を合わせて10件まで。超えるときは重い順に10件を載せ、残りは件数だけ書く
- **閉じる条件**：**重大な新規が0の回が2回続いたら閉じる**（重大＝必須の新規）。閉じたら、コメントの最初に「レビューを閉じます」と書き、それ以上回さない
- **差分の外の気づき**：今回の変更の外で見つけたことは、作業チケットにして（`gh issue create`）コメントに番号だけ書く。必須にしない。PR は止めない

## コメントの型

```
## AI レビュー 第n回（担当：api・security・state ／ 汎用：いいえ ／ 見た範囲：前回からの差分と未解決 n件）

### 前の指摘
| 番号 | 状態（解決・見送り・未解決） | メモ |

### 必須 n件（新規）
| 番号 | 場所 | 内容 | 見つけた担当 | 直し方の案 |
### 推奨 n件
### 細かい n件
（上限を超えた分：n件）

### 差分の外の気づき（作業チケット）
- #番号 …

### 未カバー（人が見る所）
- 割り振りなし：…
- レビュー役が確かめられなかった所：…
- 重要な所の変更：…

重大な新規：n件（0の回が続いた回数：n／2）
```

## 終わってよい条件

- 割り振られた担当が**すべて**結果を返し、合わせた結果が PR にコメントしてある
- 前の指摘すべてに、解決・見送り・未解決のどれかが付いている（2回目から）
- 未カバーの節がある（0件なら「なし」と書く）
- `.harness/reviews/pr-<番号>.json` がある

## 判断チケットにするもの・しないもの

判断チケットは人の時間を使う。1回のレビューで起票するのは、次に当たる必須の指摘だけにする。同じ論点は1件にまとめる。

| 当たるもの | どう扱うか |
|---|---|
| 仕様の未確定・食い違い、顧客の合意、戻せない操作、共通部品やカタログの変更から来る必須の指摘 | 判断チケット（`/decision-memo` の型） |
| 差分の外の不足で、今の値や振る舞いに誤りが出ていないもの（検査をすり抜けうるだけ） | 判断チケットにせず、作業チケットにする。PR は止めない |
| 記録の書き方・言い回し・置き場所の好み | 推奨または細かい指摘にとどめる |
| その PR の中で直せばよいもの | 必須または推奨の指摘にとどめる（書いた側が直す） |

## 止まって人へ戻す条件

- 重要な所が未カバー（割り振りなし、またはレビュー役が見られなかった） → `ai-stop:uncovered`
- 必須の指摘が、仕様の未確定や食い違いから来ている → `ai-stop:spec-undecided`／`ai-stop:spec-conflict`
- レビュー役が返ってこない（時間切れ・失敗）。もう一度起動しても返らない → まとめずに、返らなかった担当を書いて `ai-stop:uncovered`

## してはいけないこと

- レビュー役を背景で動かして、結果を待たずにまとめる・終える
- 2回目から、差分の外まで全部を読み直して新しい論点を足す
- レビューの中でコードを直す（直すのは別の作業。書いた側に戻す）
- PR を承認・マージする
