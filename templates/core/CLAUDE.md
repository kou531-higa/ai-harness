# CLAUDE.md

AI と人の共通の規約。毎回の会話で読み込まれるので、**消したら AI が間違える行だけ**を書く（150行以内）。
手順はスキル（`.claude/skills/`）、必ず起きるべきことはフック（`.claude/settings.json`）に置く。

## 1. このプロジェクト

<!-- 1〜3行で。何を作っているか、誰が使うか -->

- 構成：`api/`（FastAPI）、`web/`（Next.js）、`infra/`（Terraform）、`docs/specs/`（仕様の正本）
- 仕様の正本はリポジトリの `docs/specs/`。ほかの場所にある仕様は写しとして扱う

## 2. 決めないこと（人へ戻す）

次の場合は実装を止め、人へ戻す。推測で埋めない。

- 仕様に TBD・要確認・保留 が残っている
- 仕様の記述どうしが食い違っている
- 同じ問題を2回直しても解決しない
- 顧客の合意が要る変更、戻せない操作、セキュリティ・個人情報に関わる判断

戻すときは `/decision-memo` で判断チケットを起票する（論点／選択肢1〜3／影響／推奨）。
ラベル `ai-stop:<理由>` を必ず付ける。理由は次から選ぶ：
`spec-undecided` `spec-conflict` `two-failures` `shared-component` `pr-too-large` `irreversible` `security` `other`

## 3. 書いてよいもの・書かないもの

- 書かない：ログ・エラー処理・認証などの土台。`api/app/core/` と `web/lib/` の共通部品を使う
- 共通部品の追加・変更が必要なら、止めて人へ戻す（`ai-stop:shared-component`）
- テストを消す・skip する変更は、理由を書いて止まる

## 4. ブランチと PR

- ブランチ名：`feat/<チケット番号>-<短い説明>`、`fix/<チケット番号>-<短い説明>`
- 1PR＝1チケット。変更は400行以内（超えそうなら分割案を出して止まる）
- PR はテンプレートの「人が判断すべき点」と「証拠」を必ず埋める

## 5. テスト

- 合格基準（AC）ごとにテストを書く。テスト名に AC の ID を入れる（例：`test_ac_001_1_...`）
- テストを先に書き、落ちることを確かめてから実装する
- 画面のテストは、固定の秒数ではなく画面の状態を待つ。要素は役割か testid で取る

## 6. 確かめ方と終わり方

- 終わる前に `make check` を実行し、コマンドと出力を示す。「通った」とだけ書かない
- 本番は読み取り専用ロールだけ。apply・マージ・本番データの変更はしない
- 1つのチケットが終わったら `/clear` する
