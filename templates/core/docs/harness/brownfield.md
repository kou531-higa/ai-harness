# 既存の案件に型を入れる

新しく作る案件より、すでに動いている案件のほうがずっと多い。この文書は、既存の案件に型をあとから入れるときの決まり。
実際の案件で、代表の「縦の1本」（1つの画面から、それが呼ぶ API・触るテーブル・関係するバッチまで）に入れて確かめた手順をもとにしている。

人の手は「判断」と「承認」だけに寄せる。コードを読む・テストを書く・直す・確かめるは AI が行う。

段階0〜3で土台を作り、そのうえで A〜D（指示から仕様を変える・共通部品・見える化・ループ）が既存の案件でも回ることを確かめた。最後に、同じ手順をループでほかの画面へ広げた。

## 0. 始める前に決めること（人）

| 決めること | 例 |
|---|---|
| 縦の1本 | 1つの業務の画面と、その API・テーブル・バッチ。同じ形のもの（明細の CRUD など）は入れない。1本でうまくいけば「ほかも同じ」と言える所を選ぶ |
| 守ること | 元のリポジトリ・DB・チケット管理・本番に書かない。試しは写しの中で閉じる（`.git` は写さない・push しない） |
| 上限 | AI の使用量・人の時間・期限。超えそうなら手前で止まって報告する |
| 完了の姿 | 何がそろったら終わりか。範囲の外は何か。報告のたびに「全体の何割・残り」を添える |

元のリポジトリと DB を守る仕組み（編集の禁止・git の書き込みと書き込みの SQL を止めるフック）を、試しの前に入れる。決まりだけでは足りない。

## 1. 段階

| 段階 | すること | 人がすること |
|---|---|---|
| 0 読むだけ | 地図を作る：画面 → API → 処理 → テーブル → バッチ。根拠（ファイルと行）を必ず付け、推測は「推測」と書く。経緯の分からない所を質問にする | 質問に答える（「不明」でよい） |
| 0.5 棚卸し | 元からある AI の型（指示書・スキル・CI・フック）を、4つの段（プロンプト・コンテキスト・ハーネス・ループ）に分けて、あるもの・ないものを並べる | なし |
| 1 土台 | 足りない所だけを足す（下の 2.）。既存のテストを流して基準（件数とコマンド）を記録する | なし |
| 2 固定テスト | 今の振る舞いをそのまま固定するテストを書き、わざと壊して落ちるかを確かめる（下の 3.） | なし |
| 3 正本と直し | 固定テストから仕様の正本（合格基準つき）を起こす。不具合は判断チケットにし、直すものは枝に置く | 直すかを決める・取り込みを承認する |
| A 指示から変える | 人の指示から、論点と選択肢を出し、正本 → テスト先行 → 作る → 検査（下の 5.） | 指示・選ぶ・承認 |
| B 共通部品 | あるのに使われていない共通部品を棚卸しし、寄せ、決まりと検査で守る（下の 6.） | 共通部品の追加・変更を認める |
| C 見える化 | 判断チケットと作業を正本1つにまとめ、画面で見せる（下の 7.） | 画面で選ぶ・認める・優先度を変える |
| D ループ | 進行役が正本を優先度順に AI に渡し、人の判断の所だけ止まる（下の 8.） | 画面で選ぶ・認める |
| 横展開 | 同じ手順を、ループでほかの画面へ広げる（下の 9.） | 同じ |

## 2. 土台：元の型を残し、足りない所だけ足す

既存の案件には、すでに指示書やスキルや CI があることがある。入れ替えずに残し、抜けやすい次の4つを足す。

1. **AI を止める設定**：push・秘密のファイル・本番・CI とデプロイと依存の固定と AI の設定の書き換えを、権限とフックで止める
2. **人へ戻す決まり**（指示書に追記。元の文は消さない）
   - 業務の振る舞いを変えること
   - 経緯の分からない「おかしく見える所」を直すこと（先に固定テストを書き、直すかは人）
   - テーブルの定義・DB の手続き・バッチの手順を変えること
   - CI・デプロイ・依存の固定・AI の設定を変えること
   - 既存のテストを消す・弱めること（変えるなら理由を書いて人に聞く）
3. **変えた所だけの検査**：変えたファイルだけ lint にかけ、テストの件数が基準より減ったら止める。元のコードの既存の警告は問わない
4. **仕様の正本と判断の記録**：合格基準ごとに守るテストを1対1で結ぶ。判断チケットは「推定・根拠・確かさ・扱い・却下した案・人の答え」

## 3. 固定テストの決まり

- **今の振る舞いを書く。** 正しいかは問わない。おかしい所は判断チケットにする
- **わざと壊して、落ちるかを確かめる。** 処理を1か所ずつ壊し、元のテストと固定テストの両方を流して比べる。最初から通るテストは、何も見ていないおそれがある
- **「落ちたテスト 0件」を信じない。** テストが1件も流れていなくても 0件と出ることがある。通った件数まで見る
- **書いた中身・送った中身を確かめる。** 「成功が返る」「呼ばれた」だけでは、壊しても気づかない
- **既知の不具合は「あるべき」で書いて、今は落ちることを確かめる**（Jest・Vitest の `it.failing`）。直したら知らせてくれるので、そのとき通常のテストに変える
- **例のデータは本物の形から作る。** 既存テストの例のデータは、本物とずれていることがある。本物の変換を通して作る
- **画面と API の約束は両側で固定する。** API の入力を絞る直しは、先に画面が送る項目を固定テストで確かめてから行う

## 4. 不具合を見つけたとき

- **入口から通して読む。** 処理だけ読むと権限の穴に見えても、入口で確かめていることがある
- **型を読むだけで決めつけない。** 入力の型の既定値や変換は、全体の設定しだいで効いていないことがある
- **同じ処理が2か所にあれば、2つが同じかを確かめるテストを書く。** 片方だけ直されてずれる
- **本物の環境では試さない。** 式の振る舞いを確かめたいときは、データのない使い捨ての DB で確かめる
- **直す前に人に聞く。** 振る舞いが変わる直しは枝に置き、テストと一緒に承認をもらう。経緯が「不明」なら、今の振る舞いを正として固定テストで守る

## 5. 指示から仕様を変える（A）

人が最初に出すのは、業務の言葉の指示1つ（例：「一覧で、ある区分のものだけに絞り込みたい」）。

1. AI が今の振る舞いを読み、論点・選択肢・影響・おすすめを判断チケットにする。**選択肢の中に業務の解釈が隠れていることがある**（例：区分が空のものをどう扱うか）。コードと画面の表示の食い違いから論点を出す
2. 人が選ぶ（論点が3つで約1分）
3. AI が正本の合格基準を先に直し、テストを先に書き、**作る前に新しいテストだけが落ちることを確かめる**
4. 作る → 変えた所だけの検査 → 人が取り込みを承認する

正本を先に直す順番は、AI が後回しにしやすい。テストの番号が正本にあるかを確かめる検査があるとよい。

## 6. 共通部品（B）

- **棚卸しは「あるか」ではなく「使われている数と手書きの数」を並べる。** 既存の案件では、共通部品がないのではなく、あるのに使われていない所とない所が混ざっている
- 寄せるときは振る舞いを変えない。固定テストが通ることと、**共通部品をわざと外すとテストが落ちること**の両方を確かめる
- 指示書に「共通部品を使う。ない・足りないときは人に聞く」と共通部品の一覧を書く
- 変えた所だけの検査に2つ足す：(1) 共通部品を使わない書き方を、**新しく足した行だけ**で止める（元のコードは問わない）(2) 重複の行が基準より増えたら止める。わざと違反を入れて、全部止まるかを確かめる（最初は半分しか止まらなかった）
- 「共通部品を付けたのに、中でも手書きしている」所は、数え直すと実際より少ないことがある。AI に数え直させ、振る舞いが変わる所（確定のあとに外の仕組みを呼ぶ処理など）は寄せずに人に聞く。寄せないものは、今の振る舞いを固定テストで守る
- 業務の判定（区分の判定など）は、判定の表を正本にし、API と画面それぞれ1か所の関数にまとめ、**同じ表の例で両方を確かめる**

## 7. 見える化（C）

- **正本はリポジトリの中のファイル1つ**（判断チケットと作業。状態・優先度・担当・選択肢・人の答え）。画面と進行役が同じものを読む
- 案件の情報を外に出せないなら、外のサービスや公開のページを使わず、**手元だけで開く画面**にする（127.0.0.1 だけで待つ）
- 人が画面でできること：優先度を変える・判断待ちの選択肢を選ぶ・承認待ちを認める／差し戻す・止まった作業をやり直させる。押すたびに人の時間の記録に1行足す
- 数字は手で書かない。テストの件数・重複の行は検査が書き出し、人の時間は記録から数える
- 選択肢ごとに「次は誰の番か」を持たせる。元の案件に入れるなど AI がしてはいけない作業は、人が選んでも人の番のまま
- 画面の作りを変えたら、サーバーを立ち上げ直す（古い作りのまま動いて、承認のボタンが出なかった）

## 8. ループ（D）

1回の巡回で、進行役は次を行う（型を回す役の決まりは `operator.md`）。

1. 人が認めた枝を取り込み、検査が通らなければ戻す
2. 正本から「AI の番」の作業を優先度順に1つ選ぶ（人の番・進行役そのものは選ばない）
3. 作業ごとの枝を作り、AI に1件だけ渡す
4. AI は4つの終わり方のどれかで終える：**done**（承認待ちへ）・**need_decision**（選択肢とおすすめつきで判断待ちへ）・**split**（小さい作業に分けて、親のすぐ後ろの優先度で足す）・**blocked**
5. **検査は進行役が流す。** AI の「通った」をそのまま使わない。落ちたら1回だけ直させ、それでも落ちたら人へ
6. 結果で正本を更新する。AI が動けなかったときは、作業を AI の番に戻して巡回を止める

決まり：

- **本線は人が認めるまで変わらない。** 1件ずつ・枝ごと・人が認めたら取り込む
- **人が判断に答えた作業は「続き」として扱う。** 枝を作り直すと前回の AI の作業が消える。本線とぶつかったら、AI に本線を取り込ませ、ぶつかった所を直してから続けさせる
- **元の案件の守りを、ループの AI にも同じ形で効かせる。** AI の起動のしかたによっては、全体の設定（守りのフック）が読まれない
- **進行役そのものにテストを書く。** 使い捨ての git と偽の AI で、状態の移り方を確かめる。進行役の穴7つのうち4つは、実際に回して初めて見つかった。見つけたら、その場合のテストを足す
- **検査の範囲は、AI が触る範囲に合わせて広げる。** 最初の縦の1本の範囲のままだと、ループが触ったほかのモジュールを見ていない
- 毎回、AI の操作の記録で「元の案件を指す呼び出し・push・拒否された操作」を数える（試しではすべて 0）

## 9. 横に広げる

- 縦の1本で作った手順（正本の合格基準 → 固定テスト → わざと壊す → 検査の基準を上げる）を、そのままループの作業にする
- 大きい作業は、AI が自分で分ける（split）。分けた作業は、人が何もしなくても次の巡回で進む
- 実際の試しでは、3つの画面で**手順が雛形のまま当てはまり、直した所はなかった**。そのうち1つで、縦の1本で直したものと同じ形の不具合を AI が自分で見つけ、決めずに止まった。人が「直す」を選ぶと、次の巡回で直した

## 10. 測ること

| 測るもの | 見方 |
|---|---|
| 壊したことに気づけた割合 | 元のテスト 対 固定テスト。壊し方ごとに記録する |
| 人の時間 | 答えた・承認した・画面で押した回ごとに記録する |
| 型を入れる手間 | 雛形のまま使えた所と、直した所 |
| ループ | 作業ごとの AI の時間・手数・費用と、終わり方（done・need_decision・split・blocked）の数 |

実際の案件での試しでは、処理を85通り壊して（縦の1本で45通り、横に広げた3つで40通り）、元のテストが気づけたのは21通り（25%）、固定テストは84通り（99%）だった。人の時間は、段階0〜3で約14分、A〜D と横展開を含めて合計約31分（答え・承認・画面で押した回だけ。コードは書いていない）。ループは4回の巡回で、AI が6件の作業を合計約29分で進めた。

## 11. 終わったら持ち帰るもの

- 結果のまとめ（数字と学び）
- 元の案件に入れる場合の提案一式（差分を中身ごとに分け、振る舞いが変わるものを明記する）。写した直後の状態に当てて、試しの写しと同じになるかを確かめる。固定テストが直したあとの振る舞いを確かめる場合は、まとめて当てる前提にする。入れるかは人が決める
- 雛形への学び（業務の言葉を外して一般化し、この文書に戻す）
