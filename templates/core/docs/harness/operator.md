# 型を回す役を AI にする

チケットを AI に渡し、レビュー・直し・CI・マージまで流す「型を回す役」（オペレーター）は、最初は人がしがちになる。
何を流すか選び、計画に OK を出し、止まった理由を調べ、人への報告をまとめる。
この役も AI に移せる。人が残すのは「人でないと決められないこと」だけにする。

この文書は、台本（`claude -p` で AI を動かすシェルや Python）で巡回を組むときの決まり。動かし方の決まりは `headless.md`、並べ方は `parallel.md`。

## 1. 人に残すこと

| 人がすること | 伝え方 |
|---|---|
| 判断チケットで選ぶ | 選んだ案をコメントして閉じる |
| 型の設定・共通部品を変える PR を認める | 中身を見て、PR に `owner-approved` のラベルを付ける |
| どこまで AI に任せるかを決める | 基準のファイル（下の 3.）を直す |
| 止まったまま AI が直せなかったものに指示する | チケットにコメントする |

## 2. 1回の巡回

1. **片づけ**：前の実行が残した作業場所（変更のないもの）を外す。残っていると、同じブランチを取り合う
2. **認められた PR をマージ**：`owner-approved` が付いた PR を、検査と衝突を確かめてから `merge_pr.py` でマージする
3. **選ぶ**：開いたチケットから、AI だけで最後まで進められるものを AI が選ぶ。基準：
   - 人の判断が要るもの（「〜かを決める」・顧客の合意・業務の扱いが未定）は選ばない
   - 同じファイルを触りそうなものは順番にする（同じ1行に書き足すものも）
   - 前に止まった・選ばなかったチケットは、そのあと動き（コメントなど）があるまで選ばない
4. **人の判断の準備**：選ばなかったうち、上から決まった件数を、AI が判断チケット（論点・選択肢と影響・推奨・決定者と期限）にする。人は選ぶだけにする。もう済んでいたものは、証拠を書いて閉じる
5. **流す**：選んだチケットを、`/feature` → `/review` → 直す → CI → マージの順に流す（`parallel.md` の決まりで並べる）
6. **直す**：止まった理由を読み分け、AI が1回だけ手を入れてやり直す（下の 4.）。2回目は人へ
7. **取りまとめ**：1日1枚の確認のチケット（`owner-digest`）を作るか、同じ日のものを書き直す（下の 5.）。前の日のものは閉じる

## 3. 任せる範囲は、人が基準として決める

台本は、人が書いた基準のファイルを読んで動く。例：

```json
{
  "pick": 3,
  "max_par": 3,
  "memos_per_cycle": 2,
  "plan_ok_by_ai": true,
  "retry_once": true,
  "merge_approved": true,
  "skip_labels": ["needs-decision", "owner-digest", "ai-stop:"]
}
```

- `pick`・`max_par`：1回に選ぶ数と、並べる数
- `memos_per_cycle`：1回に何件まで判断チケットにするか（多いと、人の判断待ちが一度に積まれる）
- `plan_ok_by_ai`：計画への OK を AI に任せるか（任せるのは、決定・決まり・仕様に反せず、新しい判断も要らないときだけ）
- `retry_once`：CI の失敗・途中の失敗・マージの失敗を、AI が1回直してやり直すか
- マージの条件（必須の指摘0・CI 通過・新しい判断なし・行数の基準内）と、型の設定・共通部品を止める線は、基準のファイルでは緩めない。`merge_pr.py` と CLAUDE.md にある

## 4. 止まった理由の読み分け

| 止まり方 | AI がすること |
|---|---|
| PR がなく、計画を書いて止まった | 確かめる AI が、計画を決定・決まり・仕様と照らす。反していなければ「計画への OK」をコメントして続ける。新しい判断が要れば判断チケット |
| PR がなく、「もう済んでいる」と止まった | 確かめる AI が、証拠を確かめ直して閉じる。作業した AI の最後の答えも渡す（計画も証拠も、答えの中にしかないことがある） |
| 判断チケットを起こした | 待つ。判断チケットが閉じたら、決定をチケットにコメントして続ける |
| CI が通らない | 失敗の記録（`gh run view --log-failed`）を読み、PR が原因なら直す。関係のない失敗なら、空のコミットで回し直す |
| main と衝突した | main を取り込んで直す（`parallel.md` の 6.） |
| 型の設定・共通部品を変える | 待つ。取りまとめの「認める」に出す |
| 必須の指摘が2回とも残った・同じ失敗が2回 | 人へ（取りまとめの「止まったまま」に出す） |

## 5. 取りまとめ（1日1枚）

人がすることだけを、順に並べる。

1. **選ぶ**：開いた判断チケット。決定者ごとに分け、それぞれ推奨の1行と、開いてからの日数
2. **認める**：型の設定・共通部品を変える PR（まだ `owner-approved` がないもの）
3. **見る**：AI が1回直してもだめで、止まったままのもの。理由つき
4. 参考：人の判断が要りそうで、まだ判断チケットにしていないもの（多ければ上から15件と残りの件数）
5. 今回済んだもの（マージした・済んでいたので閉じた）と、AI の費用

報告は1か所（このチケット）に集める。人は、これを見るだけで1日の仕事が分かるようにする。

## 6. 分かっている限界

- **誰が承認したかを見分けられないことがある**：AI と人が同じ GitHub のアカウントで動いていると、`owner-approved` を付けたのが誰かを見分けられない。AI には付けさせない決まり（CLAUDE.md）にしているだけで、仕組みでは止まらない。分けられるなら、AI 用のアカウント（GitHub App など）で動かし、ラベルを付けた人を確かめる
- **AI の答えの形**：選ぶ役・確かめる役の答えは、最後に決めた形（JSON や `VERDICT:` の行）で受け取る。長い答えを途中で切ると、決めた形の部分が読めなくなる。答えは全文を残す
- **費用**：巡回ごとに AI の費用がかかる。回す間隔は人が決める（毎日・平日の朝だけ・手で回す、など）
